Foundation Web App — Build Guide & UI Kit

A short, buildable plan for a small NGO site: decided stack, modules & roles, data model, folder structure, a simplified phased roadmap (no CI/CD), and minimalist UI mockups for every page.

Working assumptions (your written answers didn’t arrive in the message — correct any and I’ll revise): small NGO, modest traffic, single language & currency · Stripe for online donations, one-off now with recurring later · emailed receipts, donors may opt in to contact · four staff roles (Owner, Admin, Finance, Editor) · offline/cash donations are recorded · “activities” are storytelling content (no ticketed events yet). Per your note, no CI/CD — deploys are a simple git push to Vercel.

1Tech Stack decided · one choice each

Chosen for the fewest moving parts: one codebase (Next.js does the public site, admin, and API), one database, managed hosting. Nothing here you have to operate yourself.

framework

Next.js (App Router) + TypeScript

One project serves public pages (SEO-friendly SSR), the admin UI, and the API route handlers. Fewer parts than a separate frontend + backend.

styling

Tailwind CSS

Utility-first, minimalist by default. Add shadcn/ui for ready-made accessible components.

database

PostgreSQL + Prisma ORM

Managed Postgres (Neon or Supabase). Prisma gives typed queries + migrations. Parameterised by default → no SQL injection.

auth

Auth.js (NextAuth) — credentials + roles

Email/password with hashed passwords, JWT/session, role stored on the user. Add TOTP MFA for Owner/Admin later.

payments

Stripe Checkout + webhook

Hosted checkout keeps cards off your servers. A signed webhook is the only source of truth for donation status.

email

Resend (transactional)

Receipts, invites, password resets, contact alerts. One API, simple templates.

file storage

Cloudflare R2 / S3 (via UploadThing)

Media never touches the DB or app disk. UploadThing keeps signed-upload wiring trivial for a small team.

hosting

Vercel + managed Postgres

Push to deploy. Preview + production environments come built in — no pipeline to maintain.

safety net

Sentry + managed DB backups

Error tracking and automatic daily backups (point-in-time restore). The two things worth not skipping.

Prefer a separate backend? Swap the API layer for a small Express or NestJS service and keep everything else. Not necessary at this size, but supported by the same data model and folder split.

2Function Modules & Roles

Ten modules cover the whole app. Each notes which roles act on it. Authorization is enforced server-side in every API route — the UI only hides what the backend already forbids.

Public Website

Home, About, Programs (list + filter), Activity detail, Contact, legal & error pages.

Public — read published content, submit contact form.

Auth & Accounts

Login, invite-based onboarding, email verify, password reset, sessions. MFA for privileged roles (later).

All staff — own account. Owner — invite/deactivate users.

Content (Activities)

CRUD with draft → in-review → published → archived. Categories, per-activity SEO fields.

Editor — create/edit own drafts, submit. Admin/Owner — approve & publish.

Media Library

Upload to object storage, validate type/size, thumbnails, alt text.

Editor — upload to own drafts. Admin/Owner — manage all.

Donations & Payments

Stripe checkout, webhook confirmation, receipts, offline entry, refunds.

Public — donate. Finance — reconcile, refund, add offline. Admin/Owner — view.

Admin Dashboard

At-a-glance metrics, approval queue, contact inbox — the daily landing screen.

All staff — role-scoped view.

Reporting

Donation totals by date/category/status, gross/fees/net, CSV export.

Finance/Admin/Owner — view & export.

Users & RBAC

Roles, permission checks, invitations, deactivation.

Owner — full control. Others — none.

Audit Log

Immutable record of logins, role changes, donation edits/refunds, deletes.

Admin/Owner — read. System — write.

Settings

Org details, SEO defaults, category management; integration keys (Owner-only).

Admin — safe settings. Owner — dangerous settings/keys.

Role & permission matrix

3Data Model Prisma-style, brief

Nine tables. Note the fields that make donations safe: a unique providerPaymentId (idempotent webhooks + reconciliation), plus fee/net and an OFFLINE/ONLINE source. Content carries status, slug, author, and SEO. Soft-delete via deletedAt.

// prisma/schema.prisma (essentials)
model User      { id  name  email@unique  passwordHash  role/*owner|admin|finance|editor*/  status  createdAt }
model Invite    { id  email  role  tokenHash  expiresAt  acceptedAt? }
model Category  { id  name  slug@unique }
model Activity  { id  title  slug@unique  summary  body  status/*draft|in_review|published|archived*/
                     categoryId  coverMediaId?  authorId  publishedAt?
                     seoTitle?  seoDescription?  createdAt  updatedAt  deletedAt? }
model Media     { id  activityId?  url  type/*image|video*/  altText  createdById  createdAt }
model Donation  { id  donorName?  donorEmail?  amount  currency  fee  net
                     source/*online|offline*/  provider?  providerPaymentId?@unique
                     status/*pending|completed|refunded|failed*/  activityId?
                     receiptNo?  consentContact  createdAt }
model Contact   { id  name  email  message  status/*new|handled*/  createdAt }
model AuditLog  { id  userId?  action  entity  entityId?  meta/*json*/  createdAt }
model Setting   { key@id  value/*json*/ }  // org details, SEO defaults, etc.

5Phased Roadmap ~6–8 weeks · small team

Six lean phases. Security, accessibility, and testing are done inside each phase, not saved for the end. Discipline tags: FEBEDBSecQA

Phase 0 — Project Setup · ~½ week

Do: scaffold Next.js + TS + Tailwind; connect managed Postgres; init Prisma + first migration; base layout, design tokens & UI primitives; env vars; deploy to Vercel. DBFE
Deliver: running app, empty but deployed, DB reachable.
✓ Done when: git push deploys a live URL and prisma migrate runs cleanly.

Phase 1 — Auth & RBAC · ~1 week

Do: User model + roles; Auth.js credentials login; invite-based onboarding + email verify + password reset (Resend); rbac.ts can() helper; middleware.ts to gate (admin); login page. BESecFE
Deliver: invite → set password → login → land on role-appropriate dashboard.
✓ Done when: a non-Owner is rejected by the server (not just a hidden menu) from a users-only route.

Phase 2 — Content & Public Site · ~1.5–2 weeks

Do: Activity + Category + Media models; media upload (validate type/size, alt text); activity CRUD with draft→review→publish; public Home / About / Programs (filter) / Activity detail / Contact (honeypot + rate limit); SEO fields, sitemap, 404/500; WCAG AA pass. DBBEFEQA
Deliver: editor publishes an activity; public site shows it, accessibly.
✓ Done when: an Editor’s draft cannot appear publicly until an Admin approves it.

Phase 3 — Donations · ~1 week

Do: Donation model; Stripe Checkout create-session; webhooks/stripe endpoint (verify signature, idempotent on providerPaymentId, set status); receipt email; success page reads server-confirmed status; Finance offline-entry form. BESecFE
Deliver: a test donation is recorded only via webhook, and a receipt arrives.
✓ Done when: closing the browser before the thank-you page still records the donation correctly.

Phase 4 — Admin & Reports · ~1 week

Do: dashboard metrics; approval queue; contact inbox with status; Users management (Owner); donation report with date/category/status filters + CSV export; audit log write + viewer; settings (categories, org, SEO, keys). FEBE
Deliver: Finance exports a report; Owner invites a user; sensitive actions are logged.
✓ Done when: every donation edit/refund and role change appears in the audit log.

Phase 5 — Security, Polish & Launch · ~1 week

Do: input validation everywhere (zod), rate limits on auth/contact, secure headers + CORS, bcrypt/argon2 hashing; accessibility & mobile pass; confirm DB backups + do a restore drill; wire Sentry; connect domain + TLS; manual UAT with real staff. SecQA
Deliver: production launch with backups verified and errors monitored.
✓ Done when: a restore-from-backup succeeds and no high/critical security or a11y issue is open.

Deliberately skipped for now (your call): CI/CD pipelines, Redis, APM suites, containers, MFA (add right after launch), recurring giving, newsletter, events/RSVP, second gateway. All can slot in later without rework.

8What You’re Missing

Cheap now, expensive later — worth deciding before you start building.

A “from” email domain

Receipts/invites need a verified sending domain (SPF/DKIM in Resend) or they land in spam. Set this up in Phase 1.

Privacy policy & consent copy

You collect donor and contact emails. You need real privacy/terms text and a consent checkbox — not lorem ipsum.

Seed / first Owner account

Decide how the very first Owner is created (a one-off seed script), since there’s no one to invite them.

Refund & failed-payment policy

Who can refund, and what a donor sees if payment fails. Small, but undefined today.

Content ownership on staff exit

When an Editor leaves, what happens to their drafts? Reassign to Admin on deactivation.

Backups you’ve actually restored

Managed backups are on by default — but run one real restore drill in Phase 5 so it’s proven, not assumed.

Brand assets

Logo, colours, a few real photos and 2–3 real stories — the minimalist design needs real content to look finished.

Legal entity for Stripe

Stripe payouts need the NGO’s bank + registration details. Start that verification early; it can take days.

9Questions I Have

Answering these lets me tighten the plan (or the schema) precisely. Your earlier answers didn’t come through, so a couple repeat.

1. Recurring giving — one-off only at launch, or do you want monthly donations from day one? (It changes the Stripe setup: Checkout vs. subscriptions.)
2. Currency & payout country — which single currency, and which country is the NGO registered in (for Stripe)?
3. Team size building this — solo developer, or a small team? (Only affects the timeline, not the plan.)
4. Roles — is the four-role model right, or will the same person handle both finance and content (fewer roles)?
5. Editor approval — confirm Editors must get Admin approval before publishing (recommended), vs. trusted-publish.
6. Newsletter — in scope now, later, or not at all? If yes, which provider (Mailchimp, Resend audiences)?
7. Languages — English only, or must the public site be multilingual? (Best decided before building pages.)
8. Domain & email — do you already own the domain and a business email to send receipts from?
9. Content volume — roughly how many activities/year? (Tells me whether to add search now or later.)
10. Existing data — any past donation records or content to migrate in, or a clean start?
